## 摘要

大规模 AI 编程的关键，不是同时启动更多 Agent，而是把研究、决策、执行和验收分开：强模型制定方案与规范，小模型批量处理边界清晰的任务，Git 和追踪表维护协作状态，PoC、截图与主分支验证构成质量闭环。AI 因此不再只是代码补全工具，而成为一支有分工、有约束、有证据验收的工程团队。

## 正文

### 从代码助手转向工程生产线

一个超过一万行 CSS 的项目在一天内迁移到 StyleX，靠的不是让 Agent 直接开始改代码，而是先把迁移过程组织成一条明确的生产线：

```text
风险扫描 → 清理死代码 → 确定迁移方案
         → 单模块 PoC → UI 验证
         → 建立追踪表 → 多 Agent 并行迁移
         → 主 Agent 合并审查 → 截图验收 → 提交
```

这条流程先减少未知风险，再验证迁移模式，最后才扩大并发。每个阶段都有明确输入、交付物和验收方式，避免把模型的“已经完成”当成事实。

### 先研究和验证，再扩大执行规模

迁移开始前，先让 AI 扫描整个项目，识别特殊场景、边界条件和潜在风险，而不是立即写代码。快速迭代的项目通常积累了大量死代码，先清理无效样式，可以避免迁移没有价值的内容，也能缩小后续任务范围。

随后只选择一个模块制作 PoC，并通过迁移前后的 UI 对比产出验证报告。PoC 的作用不是展示进度，而是确认 StyleX 的技术方向、迁移模式和验收方法在真实项目中都可行。只有这一闭环成立后，才启动全量迁移。

### 用模型能力分层，而不是让所有 Agent 自由发挥

不同角色承担不同层次的判断：

|角色或机制|主要职责|关键边界|
|---|---|---|
|强模型|研究风险、确定方案、编写迁移手册、合并审查|负责架构判断和规则，不承担所有重复劳动|
|小模型 Worker|依据手册迁移不同模块|执行已定义模式，不重新设计整体方案|
|Git worktree 与追踪表|隔离工作区、记录模块状态、支持合并与回滚|让并行协作状态显式化|
|PoC、截图和主分支验证|证明方案可行并检查视觉一致性|以真实产物作为完成标准|

强模型把隐性的架构判断固化为可复用的“模块迁移手册”，小模型只在清晰边界内批量执行。这样既能利用小模型的成本优势，也能减少多个 Worker 各自发明迁移方式造成的分叉。

### 用隔离、审查和证据形成质量闭环

每个 Worker 在独立的 Git worktree 中处理一个模块，避免并行修改相互污染。完成后由主 Agent 统一合并、解决冲突，并在主分支进行 UI 验证；不符合要求的结果退回重做，而不是因为代码已经生成就直接接受。

视觉迁移尤其适合截图验收。每个阶段都保留迁移前后的组件截图和验证文档，把“看起来应该一致”变成可以审查的视觉证据。完整的提交历史则记录每一步变化，使过程可追溯、可审查、可回滚。案例中保留了 300 多条提交，而没有为了整洁压缩 AI 的工作轨迹。

### 案例结果与成本

据作者统计，迁移后 CSS 生产体积从 215.7 kB 降到 102.3 kB，多个 Worker 累计消耗约 30 亿 token。这说明多 Agent 可以显著压缩日历时间，但并不意味着计算成本很低。是否值得采用这种方式，应同时衡量迁移收益、人工审查成本和模型消耗。

### 适用边界

这套方法特别适合 CSS 迁移，因为任务可以按组件切分，Worker 之间依赖较少，结果又能通过截图直观验收。它不适合直接照搬到所有工程任务：架构重构、复杂业务逻辑或缺少明确验收标准的项目，往往存在跨模块耦合和隐性决策，并发规模越大，合并和纠偏成本可能越高。

可复用的原则不是“多开几个 Agent”，而是先把问题结构化，把可并行的工作切开，用统一规范约束执行，再用外部证据而非模型自述判断是否完成。这与 [[AI 编程基本功的核心是组织并验证复杂性]] 的结论一致：模型可以改变执行方式，但不能省略复杂性管理和质量验证。
