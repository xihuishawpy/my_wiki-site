## 摘要

长对话的压缩策略需要同时考虑未来输入成本、摘要调用成本、缓存前缀冷启动、信息损失和上下文质量。缓存对齐摘要通过保持原请求前缀不变、只在末尾追加总结指令，降低生成摘要本身的成本；压缩后的新摘要则会形成一次新的缓存前缀。

## 正文

这份笔记整理了三个相关概念：

- 缓存前缀：为什么压缩后第一次请求会有一次缓存失效成本。
- 动态压缩决策：什么时候该压缩，应该保留多少。
- 缓存对齐摘要：生成摘要这一步怎么尽量便宜。

它们解决的是同一个问题：长对话越来越贵、越来越接近上下文上限，但压缩本身也不是免费的，所以要聪明地压。

---

### 1. 先理解 prompt cache 是什么

很多大模型 API 会对请求开头的 token 做缓存。

简单说：

```text
第 1 次请求：
[system][tools][历史 A][历史 B][用户问题 1]

第 2 次请求：
[system][tools][历史 A][历史 B][用户问题 2]
```

第 2 次请求开头的：

```text
[system][tools][历史 A][历史 B]
```

和第 1 次请求是连续一致的，所以这段可能命中缓存。

命中缓存后，这部分输入 token 通常会比全价便宜很多。

重点是：缓存不是看“语义差不多”，而是看“请求开头的 token 序列是否连续一致”。

---

### 2. 缓存是绑定 session 吗？

不准确。

更准确的说法是：缓存通常绑定的是“请求前缀内容”，而不是你前端看到的某个“对话 session”。

也就是说：

- 同一个 session 里，如果请求前缀变了，也可能缓存失效。
- 不同 session 里，如果前缀内容、模型和相关配置一致，也有可能复用缓存。

具体能不能跨 session 复用，要看服务商实现。

但理解原理时，可以先记住一句话：

> prompt cache 主要看请求开头是否和之前完全一致，不是单纯看 session ID。

---

### 3. 为什么压缩会改变缓存前缀

长对话压缩后，旧历史会被摘要替换。

压缩前：

```text
[system][tools][用户 A][助手 B][用户 C][新问题]
```

压缩后：

```text
[system][tools][摘要 S][保留的用户 C][新问题]
```

虽然 `摘要 S` 表达了 `用户 A` 和 `助手 B` 的含义，但它的 token 序列和原来的 `用户 A + 助手 B` 完全不同。

所以缓存匹配到这里会断：

```text
[system][tools] 还能命中
[摘要 S] 第一次出现，旧缓存对不上
```

这就是“压缩会改变缓存前缀”的意思。

---

### 4. “第一次缓存失效成本”是什么意思

压缩后第一次请求：

```text
[system][tools][摘要 S][保留消息][新问题 1]
```

服务端以前没见过 `[摘要 S][保留消息]` 这个新前缀，所以这部分可能要按更贵的方式计费。

但下一次如果还是这个前缀：

```text
[system][tools][摘要 S][保留消息][新问题 2]
```

那它就可能重新命中缓存。

所以这个成本通常不是永久的，而是新摘要第一次进入请求时的一次冷启动成本。

---

### 5. 上下文压缩到底在做什么

压缩的目的不是把历史简单删掉，而是把旧历史变成一个较短的摘要。

原来：

```text
[system][tools][很长很长的旧历史][最近消息][新问题]
```

压缩后：

```text
[system][tools][旧历史摘要][最近消息][新问题]
```

这样做有三个好处：

- 请求变短，成本下降。
- 不容易超过模型上下文上限。
- 上下文更干净，模型更不容易被很久以前的噪声干扰。

但它也有代价：

- 生成摘要本身要花钱。
- 新摘要会带来一次缓存前缀变化。
- 摘要可能丢细节。

所以不能只看“历史长了就压缩”，还要算压缩是否值得。

---

### 6. 动态压缩决策：不是等一个固定阈值

bash-agent 的动态压缩思路是：

> 每次检查是否要压缩时，不只判断 token 是否超过阈值，而是估算压缩后的净收益。

它主要回答两个问题：

1. 现在要不要压缩？
2. 如果压缩，应该保留多少最近消息？

这里的“保留多少”不是固定 N 条，而是枚举很多候选值 `k`，看哪个收益最高。

---

### 7. 动态压缩在算哪笔账

可以把它理解成下面这个公式：

```text
净收益 =
  后续少带旧历史省下的钱
- 新摘要前缀造成的一次缓存失效
- 生成摘要的 summary call 成本
- 摘要丢细节的信息损失
+ 上下文变短带来的质量改善
```

如果净收益大于 0，就值得压缩。

如果净收益小于等于 0，就暂时不压缩。

---

### 8. 五项收益/成本分别是什么意思

### 8.1 后续节省

压缩后，后续请求不用再带很长的旧历史。

例如旧历史有 60k tokens，未来还会调用模型很多次，那每次少带这 60k，就能省不少钱。

未来对话越长，这一项越大。

### 8.2 缓存失效

压缩后会出现新摘要：

```text
[summary S][保留消息]
```

这段新前缀第一次出现时，服务端没见过，所以会有一次缓存失效成本。

### 8.3 summary call 成本

生成摘要需要额外调用一次模型。

这次调用也会消耗输入 token 和输出 token。

### 8.4 信息损失

摘要不是原文。

它可能漏掉文件路径、错误信息、用户偏好、已经做过的尝试等细节。

压缩次数越多，信息损失风险越高。

### 8.5 质量改善

上下文太长时，模型可能会遗漏中间信息，或者被过期信息干扰。

压缩后上下文更短、更干净，模型后续回答质量可能更好。

这个改善也算作收益。

---

### 9. 什么时候会更倾向于压缩

通常这些情况更适合压缩：

- 历史已经很长。
- 未来还会有很多轮调用。
- 上下文快接近模型上限。
- 旧历史大部分已经不需要逐字保留。
- 当前上下文太乱，已经影响模型表现。

这些情况则要谨慎压缩：

- 对话刚开始，历史还不长。
- 未来可能只剩一两次调用。
- 刚刚压缩过，继续压缩可能丢细节。
- 当前任务依赖旧历史里的精确日志、代码片段或错误输出。

---

### 10. 为什么要“保留最近消息”

压缩不是把所有旧内容都变成摘要。

通常会保留最近几轮原始消息，因为最近消息往往包含：

- 用户最新目标。
- 当前正在编辑的文件。
- 最近的报错。
- 刚刚达成的决定。
- 工具调用的最新结果。

旧历史可以摘要，最近上下文最好保留原文。

---

### 11. 为什么切点要对齐到 user message

假设历史是：

```text
user A
assistant A
tool A
user B
assistant B
user C
```

如果压缩切点从 `assistant B` 中间开始，就会破坏一轮完整交互。

更好的方式是把切点向前移动到 `user message` 边界：

```text
[summary S]
[user B]
[assistant B]
[user C]
```

这样后续模型看到的是完整 turn，不会看到半截 assistant/tool 结果。

---

### 12. 缓存对齐摘要是什么

缓存对齐摘要解决的是另一个问题：

> 生成摘要这一步本身，怎么尽量便宜？

错误做法是单独构造一个全新的摘要请求：

```text
[新的 system: 你是摘要器]
[旧历史]
[请总结]
```

这样请求结构变了，缓存前缀可能从开头就断。

正确做法是保持正常请求结构不变，只在最后追加总结指令：

```text
[原来的 system]
[原来的 tools]
[旧 summary，如果有]
[历史消息 A]
[历史消息 B]
[历史消息 C]
[追加一句：请总结以上历史]
```

这样前面的大部分内容和之前正常对话请求一致，有机会命中 prompt cache。

新增的主要只有最后那句总结指令。

---

### 13. 缓存对齐摘要和压缩后缓存失效不是一回事

这两个概念容易混淆。

缓存对齐摘要说的是：

> 生成摘要的 summary call，怎样复用旧请求缓存，避免全价重新提交历史。

压缩后缓存失效说的是：

> 摘要生成完成后，后续请求用 summary 替换旧历史，新 summary 第一次进入请求时，会形成新前缀。

它们发生在不同阶段。

完整过程是：

```text
阶段 1：正常对话
[system][tools][历史 A][历史 B][新问题]

阶段 2：缓存对齐摘要请求
[system][tools][历史 A][历史 B][追加：请总结]
=> 旧历史大部分可命中缓存

阶段 3：后续压缩后请求
[system][tools][summary S][保留消息][新问题]
=> summary S 第一次出现，可能有一次新前缀成本

阶段 4：再下一轮
[system][tools][summary S][保留消息][新问题 2]
=> 新前缀稳定后可重新命中缓存
```

---

### 14. 在一次对话中，怎么做到缓存对齐摘要

前提是你在 API 或 agent 层能控制请求消息数组。

### 第一步：不要改请求开头

不要换 system prompt。

不要换 tools 顺序。

不要把“请总结”放到最前面。

不要先删掉历史再请求总结。

### 第二步：在正常请求末尾追加总结指令

例如正常请求是：

```text
[system]
[tools]
[旧 summary，如果有]
[message A]
[message B]
[message C]
[用户新问题]
```

缓存对齐摘要请求应该是：

```text
[system]
[tools]
[旧 summary，如果有]
[message A]
[message B]
[message C]
[用户新问题]
[请总结以上历史，保留关键决策、文件、错误、约束和下一步]
```

这样前面的内容尽量和正常对话保持一致。

### 第三步：保存模型输出的摘要

模型返回摘要后，把它保存成类似：

```text
summary.txt
```

或者保存在会话状态里。

### 第四步：后续请求用摘要替换旧历史

后续请求变成：

```text
[system]
[tools]
[summary S]
[保留的最近几轮消息]
[用户新问题]
```

这一步才是真正把长历史压短。

---

### 15. 如果是在 ChatGPT 网页里能做到吗？

很难精确做到。

因为在 ChatGPT 网页里，用户不能完全控制底层 API 的 messages 数组、system prompt、tools 排列和缓存策略。

你可以手动说：

```text
请总结当前对话，保留关键上下文
```

但这不等于严格意义上的缓存对齐摘要。

真正的缓存对齐摘要通常发生在自己写 agent、CLI、服务端或 API 调用时。

### 16. 一个 Python 版示例：用 Qwen API 做缓存对齐摘要

Qwen 的 DashScope 服务支持 OpenAI-compatible 调用方式，所以可以直接用 `openai` Python SDK。

先安装依赖并设置环境变量：

```bash
pip install openai

# PowerShell
$env:DASHSCOPE_API_KEY="你的 DashScope API Key"
```

下面这段代码保留了核心流程：

1. 先判断是否值得压缩。
2. 如果值得压缩，保留最近几轮消息。
3. 用“原请求结构 + 末尾总结指令”生成摘要。
4. 后续请求用“摘要 + 最近消息”替换完整旧历史。

```python
import os
from dataclasses import dataclass
from typing import Any

from openai import OpenAI


client = OpenAI(
    api_key=os.environ["DASHSCOPE_API_KEY"],
    # 中国区 DashScope 默认地址。国际站可改成：
    # https://dashscope-intl.aliyuncs.com/compatible-mode/v1
    base_url=os.getenv(
        "DASHSCOPE_BASE_URL",
        "https://dashscope.aliyuncs.com/compatible-mode/v1",
    ),
)


SUMMARY_INSTRUCTION = """
请总结以上历史，用于后续继续完成同一个任务。

必须保留：
- 用户目标和明确约束
- 已经做过的关键操作
- 重要文件路径、函数名、命令和配置
- 报错信息、失败尝试和当前阻塞点
- 已经达成的决定
- 下一步应该继续做什么

不要编造没有出现过的信息。
""".strip()


@dataclass
class Session:
    system_message: dict[str, str]
    messages: list[dict[str, str]]
    tools: list[dict[str, Any]] | None = None
    summary: str | None = None


@dataclass
class CompactDecision:
    should_compact: bool
    keep_count: int


def estimate_compaction_benefit(messages: list[dict[str, str]]) -> CompactDecision:
    """
    这里放动态压缩决策逻辑。

    真实实现可以估算：
    - 当前历史 token 数 T
    - 保留最近消息 token 数 K
    - 被摘要替换的旧历史 token 数 H
    - 未来预计调用次数 R
    - summary call 成本
    - 缓存失效成本
    - 信息损失和质量改善

    这里为了演示，简单写成：消息超过 20 条就压缩，保留最近 8 条。
    """
    if len(messages) <= 20:
        return CompactDecision(should_compact=False, keep_count=0)
    return CompactDecision(should_compact=True, keep_count=8)


def call_qwen(
    messages: list[dict[str, str]],
    tools: list[dict[str, Any]] | None = None,
    model: str = "qwen-plus",
) -> str:
    kwargs: dict[str, Any] = {
        "model": model,
        "messages": messages,
    }
    if tools:
        # 如果正常对话使用 tools，摘要请求也要传同一份 tools，顺序也保持一致。
        # 这样请求结构才尽量和正常对话对齐。
        kwargs["tools"] = tools

    response = client.chat.completions.create(**kwargs)
    return response.choices[0].message.content or ""


def maybe_compact(session: Session) -> None:
    decision = estimate_compaction_benefit(session.messages)
    if not decision.should_compact:
        return

    keep_messages = session.messages[-decision.keep_count :]
    old_messages = session.messages[: -decision.keep_count]

    # 关键点：摘要请求不要换 system prompt，也不要把“请总结”放到最前面。
    # 它应该长得像一次正常对话请求，只在末尾追加总结指令。
    summary_request = [
        session.system_message,
        *old_messages,
        *keep_messages,
        {
            "role": "user",
            "content": SUMMARY_INSTRUCTION,
        },
    ]

    summary = call_qwen(
        messages=summary_request,
        tools=session.tools,
        model="qwen-plus",
    )

    session.summary = summary

    # 后续请求不再带完整旧历史，而是带“摘要 + 最近消息”。
    # 注意：这里的 summary 第一次进入后续请求时，会形成一次新前缀。
    session.messages = [
        {
            "role": "user",
            "content": f"以下是之前对话的摘要，请作为后续任务上下文：\n\n{summary}",
        },
        *keep_messages,
    ]


def build_next_request(session: Session, user_text: str) -> list[dict[str, str]]:
    """
    后续正常请求。
    system_message 仍然保持稳定；messages 里已经是 summary + 最近消息。
    """
    return [
        session.system_message,
        *session.messages,
        {
            "role": "user",
            "content": user_text,
        },
    ]
```

这个示例里最重要的不是 `estimate_compaction_benefit` 的简化判断，而是摘要请求的形状：

```text
[同一个 system]
[同一组 tools]
[旧历史]
[最近保留消息]
[最后追加：请总结以上历史]
```

这就是缓存对齐摘要。它尽量复用正常请求已经建立的缓存前缀，只让最后那句总结指令成为新增内容。

注意：不同 API 对 `system`、`tools`、`developer`、`assistant`、`user` 消息的组织方式不同。真实实现时要按照具体服务商的规范来构造。Qwen DashScope 的 OpenAI-compatible 模式支持用 OpenAI SDK 配置 `base_url` 调用，官方文档示例也是这种方式。

### 17. 最容易踩的坑

### 坑 1：为了摘要换了 system prompt

```text
[新的 system: 你是专业摘要器]
```

这会让请求开头变化，缓存前缀容易断。

### 坑 2：把总结指令放在最前面

```text
[请总结]
[system]
[tools]
[历史]
```

这也会改变前缀。

### 坑 3：先删历史再请求总结

如果历史已经删了，模型就没有足够内容可总结。

### 坑 4：保留消息太少

摘要可能漏掉当前任务的关键细节。

### 坑 5：保留消息太多

压缩后上下文还是很长，省不了多少钱，也没改善质量。

---

### 18. 一句话总览

```text
缓存前缀：
服务端按请求开头的连续 token 匹配缓存。

压缩后缓存失效：
旧历史被 summary 替换，新 summary 第一次出现会形成新前缀。

动态压缩决策：
先算压缩是否划算，再决定保留多少最近消息。

缓存对齐摘要：
生成 summary 时保持正常请求结构，只在末尾追加总结指令，让旧历史尽量命中缓存。
```
