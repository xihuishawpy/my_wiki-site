# Matt Pocock 与 Robert C. Martin：AI 编程为何仍需基本功

> 编号：S010 · 主题：AI 与智能系统

## 摘要

Matt Pocock 与 Robert C. Martin 讨论了编程智能体如何改变代码实现、质量控制、架构设计、规划方式和新人培养。两人的共同判断是：AI 显著降低了代码生成与修改成本，却没有消除软件复杂性；整洁代码、模块化、测试、架构和短反馈循环，仍是让人和模型持续理解、验证与修改软件的基础。

## 要点

### 代码质量仍会约束智能体

- 智能体可以更快地产生代码，也会更快地累积混乱。代码持续恶化后，它同样会在多个问题之间循环修复，速度优势随之消失。
- 基本功的意义不只是方便人类阅读，而是把复杂系统组织成有限、清晰、可验证的局部。
- 窄接口、明确职责和正确的依赖方向，可以减少完成一次修改所需的上下文。

### 关键规则应成为确定性检查

- 长提示词和不断膨胀的 `AGENTS.md` 会受到上下文稀释影响，重要规则可能被模型忽略。
- 单元测试、验收测试、突变测试、复杂度指标、架构依赖检查和端到端 QA 能给出明确的通过或失败结果。
- Robert 采用“规格整理 → 编码 → 清理 → 加固 → QA”的多智能体流水线，以更高的时间成本换取可靠性；即使如此，他估计整体仍比人工开发快四到五倍。

### 原则保留，执行方式可以调整

- 面向人类形成的具体纪律不必原样套用到智能体上。Robert 主张保留可理解、低复杂度、充分测试等价值标准，但允许调整 TDD 粒度与复杂度阈值。
- 多智能体分工的价值主要来自职责隔离和干净上下文，而不是模拟完整的公司组织结构。Matt 对后者持保留态度，但认可实现与审查分离。
- 上下文不只有容量，还有轨迹；让实现、清理和加固在不同会话中工作，可以避免前一阶段的目标持续影响后一阶段。

### 低成本修改更适合小步迭代

- 两人都反对把大量成本投入一次性的完美计划。智能体擅长扩写计划，却可能在执行时沿着遗漏现实约束的方向快速前进。
- 当一次修改的成本显著下降，更合理的方式是先完成少量用户故事，获得反馈、检查架构、重新整理，再继续推进。
- 临时规格可以帮助当下对齐，但未必需要永久保留；最终运行结果、测试和系统行为才是持续有效的事实来源。

### 人类仍需承担战略判断

- 智能体擅长战术执行，人类仍要判断应该解决什么问题、如何划分系统、哪些约束必须执行，以及何时需要停止并重组。
- 新人不能完全跳过亲自编码。没有经历实现、失败与修复，就很难识别智能体何时正在无效打转。
- Robert 建议新人先系统学习底层编程和经典软件工程，再在严格检查与资深工程师监督下完成战术任务，逐步获得管理智能体的能力。

### 共识与分歧

两人一致认为，AI 没有使软件基本功过时，而是提高了把基本功转化为机器可执行约束的价值。他们都认可模块化、自动检查、短反馈循环与人类战略判断。主要差异在于多智能体系统的规模：Robert 已采用较长的质量流水线，Matt 则只认可确实能缩小上下文和明确职责的分工，对模拟组织结构的复杂系统保持怀疑。

## 我的思考

这场对谈最有价值的区分，是“工程原则”与“人类过去执行原则的具体纪律”。AI 可以改变写代码、测试和审查的节奏，却没有改变软件需要被理解和验证的事实。与其把规范继续堆进提示词，更有效的做法是把关键要求变成测试、复杂度阈值、依赖规则和 QA 脚本，让模型在明确反馈中修正；同时保留人类对产品方向、架构边界和迭代节奏的判断。

**5:16** · 到处留下一坨坨“狗屎代码”。我当时想，这东西虽然速度很快，却也很让人沮丧，因为它反而拖慢了我。

**5:31** · 后来我换了一个思路：正因为它很快，所以它能做一些我做不到的事。二十一世纪初曾经出现过两项创新，引起了我的注意。当时我觉得，这些想法非常好，只是完全不实用。其中一个叫 CRAP，是一个缩写。

**5:58** · 它把代码覆盖率和每个函数的圈复杂度放进一个复杂的公式，最后得出一个分数，用来衡量一个函数究竟有多糟糕。二十一世纪初，我觉得这是个很棒的主意，就在当时参与的一个大型项目上跑了一遍。

**6:52** · 突变测试同样引起了我的注意。它会用一个小程序遍历源代码，把负号改成正号、小于号改成大于号、等号改成不等号，还会做其他类似修改。每修改一处，它就运行一次完整的测试套件，并且预期测试会失败，因为代码里显然发生了实质性变化。

**7:21** · 如果测试没有失败，就说明出现了一个“存活的突变体”，必须把它消灭。我在 2000 年前后，也对同一个项目运行过突变测试。当时必须让它跑一整晚，因为测试套件每次要运行四分钟，而我可能需要运行几百次。它确实找出了一批存活的突变体，我也能逐一修复，但这个方法还是不实用。

**7:45** · 我不可能把它纳入正常的构建流程。所以去年十二月，也可能已经到今年一月了，我突然想到：“等等，这些家伙速度很快，也不在乎工作有多无聊，而且会按照我的要求做事。”

**8:04** · 于是我让智能体对刚写完的所有代码运行 CRAP 分析。它运行完分析，又会根据结果清理代码。我看着它工作，觉得这还挺不错。然后我又让它运行突变测试。过去需要一整晚，现在它可能三十分钟就能完成。接着，它会堵住所有漏洞，确保每一种情况都有测试覆盖。我开始觉得，也许这就是清理“狗屎代码”的办法。

**8:32** · 这些智能体会留下大量垃圾和冗余，但我们或许有办法清理干净。于是我继续沿着这条路走，加入更多工具，不断尝试和智能体协作。最后，我终于把它们调到了能够交出不错结果的程度。现在我的原则是，先让智能体开始工作。

**8:56** · 然后让它们运行这些工具。我会努力把整个流程变成一种不需要自己查看代码的状态。

**9:06** · 我需要能够信任它们的成果。当然，我还会用其他办法验证代码质量。我会查看 CRAP 分数，确保它足够低；偶尔也会抽查代码；另外还有一大批测试需要运行。但总的来说，我的目标就是不再亲自查看代码。

**9:23** · 如果这些东西确实很快，而且我又能约束它们交出高质量成果，那我就不应该把自己的缓慢强加给它们。无论是代码审查，还是逐个细节地检查代码，瓶颈都在我身上。它们处理代码很快，我处理代码很慢。所以，我准备把代码交给它们，自己负责代码周围的东西，确保整体没有问题。目前为止，效果不错。

**9:55** · 所以你的目标是逐渐远离代码和人工审查，在代码周围搭建一套约束机制，让自己不必过多接触代码。同时尽量给智能体套上一件紧到不能再紧的束缚衣，让它没有犯错的空间。

**10:18** · 不过这里有一个前提，我想先问清楚。“狗屎代码”用英国口音说出来好像不太顺口。（笑）为什么狗屎代码不好？为什么坏代码就是坏的？这些东西速度这么快，推进得也这么快，我们为什么还要在乎代码质量，还要费力搭建这些约束？难道不能继续往前冲，直到所有缺陷都被修掉吗？
