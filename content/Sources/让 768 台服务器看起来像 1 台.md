# 让 768 台服务器看起来像 1 台

> 编号：S007 · 主题：软件与基础设施

## 摘要

关系型数据库超过几 TB 后，纵向扩容和只读副本无法解决单主节点写入、数据容量和备份耗时三个瓶颈。分片把数据和查询分散到多个主节点，再通过路由器解析、规划和分发查询，配合多个代理及可选的网络负载均衡器，把数百台服务器封装成应用眼中的一个数据库。

## 要点

Ben Dicken（[@BenjDicken](https://x.com/BenjDicken)）｜2026 年 7 月 15 日

这就是 768 台服务器。

在一些人看来，这已经是非常多的计算机了。但对于那些负责管理大型应用基础设施的人来说——这些应用拥有数百万客户，每秒执行数百万次查询——这其实很正常。达到这种规模的产品，通常需要成千上万台服务器协同工作。

在所有基础设施组件中，最难扩展的几乎总是数据库。单台数据库服务器无法承受如此巨大的负载，所以我们必须通过数据库分片，把查询和数据分散到多台服务器上。

对于数据量超过几 TB 的 Postgres 或 MySQL 数据库，分片是最有效的扩展方式。下面我们来看看，如何从一个小型的单节点数据库，扩展到一个由 4 个分片承载数 TB 数据的数据库，再进一步扩展到横跨 768 台服务器、存储 1 PB 数据的分片数据库。

### 成长的烦恼

要理解为什么分片是关系型数据库扩展过程中不可缺少的一环，我们首先需要了解其他扩展方式所面临的瓶颈。

先来看一种简单的应用架构。

你使用过的大多数应用都是以这种方式运行的，至少在它们发展的早期是如此。客户端设备上的软件通过互联网连接到应用服务器。应用服务器位于数据中心，负责身份认证、页面加载，以及所有决定应用如何运行的服务端逻辑。

所有需要持久保存的数据，例如用户账户、帖子、设置和消息，都会存入数据库服务器，并从中读取。这里所说的“数据库服务器”通常是 Postgres 或 MySQL，不过本文主要关注 Postgres。

即使使用大型数据库服务器——拥有数十个 CPU 核心和数百 GB 内存——瓶颈通常也会很快出现。最常见的是大量查询带来的 CPU 限制，或者大量读写操作造成的 I/O（IOPS）限制。

“通用可扩展性定律”（Universal Scalability Law，USL）很好地概括了这个问题。

简而言之，USL 指出：随着资源增加，资源争用会使系统的扩展能力呈次线性增长；达到某个临界点后，系统内部的不一致性甚至会导致性能下降。

Postgres 也是如此。任何试图在一台更大的服务器上，通过更多线程或进程进行横向并行扩展的软件系统，都会遇到类似的问题。

至少在短期内，一种解决办法是使用只读副本。

在这种架构中，原来的服务器继续作为主节点，同时再增加若干副本。

主节点会持续向每个副本发送消息，确保副本及时同步主节点上的数据变化。写入操作（`INSERT`、`UPDATE`、`DELETE`）只能发送到主节点。

如果允许向任意服务器写入，就可能产生互相冲突的数据。虽然可以使用复杂而缓慢的共识算法来解决这个问题，但在大多数情况下，这并不利于获得最佳性能。

不过，应用服务器可以把读取查询（`SELECT`）发送给副本。由于大多数应用的读取比例远高于写入比例，这种方式可以显著提高扩展能力。

即使查询流量并不需要副本，为了实现高可用性和数据持久性，副本通常也是必需的。

通过添加更多副本，数据库可以处理更多流量。一个极端案例是 OpenAI：它曾经为单个主节点使用了 50 个副本。

但事实证明，无论是纵向扩展服务器——增加 CPU 和内存——还是不断添加副本，都只能解决一部分问题。下面这些瓶颈无法通过这种方式消除。

#### 1. 写入受限于单台服务器

当写入量足够高时，增加再多的只读副本也无济于事。

Postgres 在确认一项写入已经提交之前，必须先把变更记录到预写日志（Write-Ahead Log，WAL）中，并将日志刷新到持久化存储。

WAL 是主节点上所有连接共享的资源。也就是说，即便数据库拥有几十个副本，整个数据库的写入最终仍然受制于这一个瓶颈。

#### 2. 副本无法提高数据容量

副本是主节点全部数据的完整复制，其中也包括所有索引。

添加副本可以提供更多执行读取操作的位置，但并没有真正把数据分散开。

#### 3. 备份

备份是确保数据持久性，以及兑现 RPO（恢复点目标）和 RTO（恢复时间目标）承诺的重要组成部分。

由于数据库节点与对象存储之间存在带宽限制，把一个庞大的单体数据库备份到对象存储中，可能需要数小时，甚至数天。

对于许多依赖频繁且经过验证的备份来运营的组织而言，这么长的备份时间是不可接受的。

解决这些问题最成熟可靠的方法，就是分片。

### 分片——是带 “d” 的 Sharding

分片通过把数据和查询分散到多个相互独立的主节点上，解决了前面提到的三个瓶颈。

从数据角度看，单个节点的存储容量和写入吞吐量都是有限的，因此分散数据很有价值。从查询角度看，网络互连和 CPU 在同一时间能够处理的查询数量也存在上限，因此分散查询同样有意义。

当数据量超过几 TB 时，无论处于什么规模，分片都会开始体现价值。

例如，对于 2 TB 数据，我们可以使用 4 个分片，每个分片存储 500 GB 数据，并承担总查询流量的四分之一。

如果需要存储 1 PB 数据——也就是 100 万 GB——就需要更多分片。在这种情况下，我们可以使用 256 个分片，每个分片包含一个主节点和两个副本，并负责存储大约 4 TB 数据。

这意味着总共需要：

```
256 × 3 = 768 台服务器
```

如果没有一套完善的系统，这种架构会给应用后端带来巨大的复杂性。面对如此多的组件，系统应该如何：

- 决定哪些数据应该存放到哪台服务器？
- 决定每条查询应该发送到哪台服务器？
- 处理需要同时访问多个分片的查询？
- 对这个分散式数据库执行备份？
- 监控整个系统的健康状况？
- 响应某台服务器发生的故障？

每一个问题都值得深入讨论。不过，本文要回答的是下面这个问题：

**怎样才能让应用把这 768 台服务器看成一个完整的数据库？**

我们希望应用服务器不再需要直接面对一个复杂的分布式系统，而是只通过一条连接字符串与数据库交互，让它看起来就像是在访问一个庞大而且可以持续扩展的单体数据库。

实际上，背后可能使用了几十个甚至几百个分片。

用于 Postgres 的 Neki 和用于 MySQL 的 Vitess 正是在解决这个问题。下面来看看它们是如何做到的。

### 代理层

在实现这一目标所需的多个关键组件中，最重要的是代理层。

代理是位于两个服务之间的中间件服务器。在这里，这两个服务分别是应用服务器和数据库服务器。

代理经常与 Postgres 数据库一起使用。即便数据库没有分片，代理仍然可以用于连接池和请求排队。

对于普通的、未分片的 Postgres 数据库，PgBouncer 是一种非常流行的代理。人们用它把来自应用的数千条连接，复用到数量更少的 Postgres 直接连接上。

PgBouncer 的目标很简单：接收来自大量客户端的众多连接，然后通过它持续维护的一组规模较小的 Postgres 连接池，对这些连接进行路由。

请求排队机制可以应对突发流量，在数据库故障转移期间也很有用。当新的主节点上线后，排队中的请求便可以继续执行。如果想进一步了解，PlanetScale 还专门发布过一篇介绍 PgBouncer 的文章。

要对 Postgres 进行分片，则需要更加复杂的代理。

最大的区别在于：除了连接复用和缓冲之外，代理还必须理解数据是如何分布在各台服务器上的，并把 SQL 查询路由到正确的分片。

因此，我们把这种代理称为“路由器”。

在插入数据时，路由器必须知道数据应该如何分布。这被称为“分片策略”。

一种常见方法，是根据某个 ID 列的哈希值对新写入的数据行进行分片。例如，向数据库插入以下数据：

```
INSERT INTO users (id, username, email) VALUES
  (1, 'ada', 'ada@example.com'),
  (2, 'grace', 'grace@example.com'),
  (3, 'linus', 'linus@example.com'),
  (4, 'margaret', 'margaret@example.com'),
  (5, 'dennis', 'dennis@example.com'),
  (6, 'barbara', 'barbara@example.com'),
  (7, 'donald', 'donald@example.com'),
  (8, 'james', 'james@example.com');
```

4 个分片分别被分配了一段需要负责存储的 ID 范围，路由器会把插入操作发送到正确的分片。

数据首先被发送到路由器。路由器计算每个 ID 的哈希值，然后把相应数据转发给正确的分片。

对于读取操作，有些查询足够简单，路由器可以直接把它们交给单个分片：

```
SELECT email FROM user WHERE id = 4;
```

在这种情况下，路由器只需要维护一份内部映射，知道每个用户 ID 位于哪台服务器上，然后把查询转发过去。

按照文章中的示例，这条查询会被发送到第一个，也就是最上面的那个分片。

另一些情况则更加复杂：

```
SELECT email FROM user
WHERE id BETWEEN 3 AND 5;
```

这个 ID 范围内的用户分布在多个分片中。

路由器必须理解数据拓扑，为查询制定分发计划，把查询发送给所有可能包含匹配结果的分片，然后在路由器中汇总结果，最后把完整的结果集返回给客户端。

归根结底，这意味着路由器本身必须内置一套完整的查询解析器和路由规划器。

路由器必须能够在同一个系统中完成查询解析、查询规划、连接池管理和缓冲。

而复杂的软件向来很难做到完全正确。

### 它怎么知道？

每个数据库都是独一无二的，拥有自己的模式、数据表和查询模式。那么，一个通用路由器怎么知道哪些数据应该存放在哪里，又该把哪些查询发送到哪里？

在 Neki 和 Vitess 中，这些信息通过表示系统数据拓扑的 JSON 文件来定义。

Vitess 的 VSchema 和 Neki 的数据拓扑配置，为工程师提供了非常大的灵活性，使他们能够精确描述数据表和查询应该如何分布。

下面是一个简化示例，展示了如何为用户表定义分片方案：

```
{
  "shard_indexes": {
    "user_hash": {
      "type": "hash"
    }
  },
  "tables": {
    "user": {
      "shard_by": "user_hash",
      "column": "id"
    }
  }
}
```

这些元数据存储在路由器中。它告诉路由器：`user` 表根据 `id` 列进行分片，并使用名为 `user_hash` 的分片索引。

`user_hash` 分片索引使用路由器内置的值哈希算法。对于每一条新写入的数据，路由器都会对 ID 进行哈希，并根据结果把数据发送到正确的分片中保存。

由于这些信息都是通过文本和 JSON 传达给路由器的，AI 智能体非常适合用来完成相关的配置和优化工作。

### 多个代理，一个数据库

当系统达到 256 个分片、横跨 768 台服务器，并且每秒执行数百万次查询的规模时，我们不可能把所有流量都送进单个代理。

我们需要许多个代理。具体可能是 10 个，也可能是 100 个，取决于流量的特征。

但我们仍然希望应用把整个系统看成一台服务器。这时，网络负载均衡器（Network Load Balancer，NLB）就可以发挥作用。

NLB 的任务很简单：通过单一主机名或 IP 地址接受连接，再把每条连接分配到多个目标中的一个。

通过这种方式，流量就能够分散到多个路由器上。一旦完成分配，一条连接在其整个生命周期中都会保持连接到同一个代理。

某些情况下，并不一定需要 NLB。

移除 NLB 会让应用服务器的连接逻辑稍微复杂一些，因为应用需要知道每个路由器的主机地址；但这样也能减少一次网络跳转，把往返延迟降到最低。

### 完整架构

现在，所有必要组件都已经到位。我们可以让一个由 768 台服务器组成、存储着 1,000 TB 数据的系统，在应用看来就像一个单体数据库。

整个连接和查询过程如下：

1. 应用服务器收到指令：“连接位于 `mydb.pscale.com` 的数据库。”
2. 系统执行 DNS 查询，返回 NLB 的 IP 地址：`123.152.100.4`。
3. 应用请求连接位于 `123.152.100.4` 的数据库。
4. 连接首先经过 NLB，然后被路由到 N 个代理中的一个。
5. 应用开始发送数据库查询。查询的路径是：

```
应用 → NLB（可选）→ 代理 → 各个分片
```

复杂的路由逻辑对应用完全隐藏。为了简化，文章中的示意图没有画出 NLB。

这个例子展示了如何扩展到 1 PB，但数据库应该在远早于这个规模的时候就开始分片。

具体建议取决于每个数据库的大小、模式和每秒查询量（QPS）。不过，对于任何超过几 TB 数据的 Postgres 或 MySQL 数据库，我们都建议进行分片。

通常正是在这个阶段，数据库开始遇到前面描述的瓶颈，例如备份耗时过长、写入能力受限等。

如果你正在面对关系型数据库的扩展难题，Neki 和 Vitess 就是相应的解决方案。

用于 MySQL 的 Vitess 已经有十多年历史，被用于扩展全球规模最大的关系型数据库。

我们拥有多年为客户运营大型分片数据库的经验，同时也是 Vitess 项目的核心维护者。

Neki 则由 Vitess 的同一批专家级维护者开发，为 Postgres 带来了一套更加强大的分片系统。

## 我的思考

分片没有消除复杂性，而是把原本暴露给应用的分布式复杂性集中到了路由层。架构能否扩展，不只取决于增加多少服务器，也取决于是否能用稳定接口、明确的数据拓扑和可水平扩展的路由器，把底层变化封装起来。
