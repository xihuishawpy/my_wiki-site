## 2. 逐项精读：决策制定（10 项）

### 2.1 Six Thinking Hats（六顶思考帽）

- **官方要义**：同一决策必须主动从多种视角审视，避免只听到最强势或最熟悉的一种声音。
- **官方步骤 / 技巧**：黄色看收益与机会；绿色不评判地生成创意；红色表达直觉和情绪；白色只看数据；黑色审视缺点与最坏情形；蓝色管理讨论过程。个人可依次换帽，团队可分角色或全体同步换帽。
- **何时适用**：高风险方案评审、跨职能意见分散、讨论陷入单一叙事，或需要把情绪纳入理性决策时。
- **AI 产品应用示例（推导）**：评审“是否上线 AI 客服自动回复”。白帽列离线准确率、转人工率和成本；黄帽看 7×24 服务与规模收益；黑帽看幻觉、越权承诺和隐私泄漏；红帽看客服与用户是否安心；绿帽提出只自动回复低风险问题、其余给草稿；蓝帽把结论收束为带门槛的灰度实验。
- **局限 / 误用风险（推导）**：帽子是视角而非证据；给人固定分帽可能固化角色或让“黑帽”被视为唱反调。必须记录事实、假设与待验证项，蓝帽也不能替代决策责任人。

来源：[Untools — Six Thinking Hats](https://untools.co/six-thinking-hats/)

### 2.2 Eisenhower Matrix（艾森豪威尔矩阵）

- **官方要义**：用“重要性 × 紧急性”区分工作，不让紧急但低价值的活动吞掉长期重要事项。
- **官方步骤 / 技巧**：逐项判断是否重要、是否紧急；重要且紧急立即做；重要不紧急排期；紧急不重要尽量委派；不重要不紧急不做。官网特别指出，重要不紧急应优先于紧急不重要。
- **何时适用**：团队任务很多、总在救火但长期目标没有进展；适合日、周或更长期的工作盘点。
- **AI 产品应用示例（推导）**：线上出现提示词注入导致数据暴露是“重要且紧急”；构建可复现评测集是“重要不紧急”；例行格式整理可委派；没有议程的“AI 灵感会”可取消。
- **局限 / 误用风险（推导）**：它按时间压力和目标贡献排序，不衡量收益大小、依赖、风险传播或机会成本；“紧急”可能由强势干系人制造。先明确季度目标和事故等级，再分类。

来源：[Untools — Eisenhower Matrix](https://untools.co/eisenhower-matrix/)

### 2.3 Second-order thinking（二阶思考）

- **官方要义**：第一步看似胜利的决策，长期可能变成损失；应继续追问后续影响。
- **官方步骤 / 技巧**：先写直接结果，再对每个结果问“然后呢？”并继续若干层；或分别问 10 分钟、10 个月、10 年后的后果。
- **何时适用**：不可逆、影响长期成本或改变行为激励的决定，例如免费策略、模型供应商、数据收集机制、自动化替代流程。
- **AI 产品应用示例（推导）**：开放无限免费推理可带来注册增长（一级），继而推高成本与滥用（二级），迫使限流并伤害高价值用户（三级）；因此一开始就设计配额、价值阈值和成本监控。
- **局限 / 误用风险（推导）**：越往后不确定性越高，容易写成故事或无限分析。给每条后果标概率、时间尺度与可验证信号，只深挖高影响路径。

来源：[Untools — Second-order thinking](https://untools.co/second-order-thinking/)

### 2.4 Decision matrix（决策矩阵）

- **官方要义**：当有多个选项和多个因素时，把比较显式化并计算加权得分。
- **官方步骤 / 技巧**：写明决策；列选项；确定因素；逐因素给选项评分；给因素权重；用“评分 × 权重”后求和；最高分作为候选胜者。
- **何时适用**：选模型、供应商、技术方案、细分市场或路线方案，且选项基本可比、评价因素较稳定。
- **AI 产品应用示例（推导）**：比较自建开源模型、托管开源模型、闭源 API；因素包括任务质量、延迟、隐私、可控性、总体成本、运维能力和供应商风险，并把合规设为准入门槛而非普通低权重项。
- **局限 / 误用风险（推导）**：数字会制造虚假的客观感，结果对权重、量表和评分者偏见敏感；补做敏感性分析，区分“硬门槛”与“可补偿因素”，保留原始证据。

来源：[Untools — Decision matrix](https://untools.co/decision-matrix/)

### 2.5 Impact-Effort Matrix（影响—投入矩阵）

- **官方要义**：按潜在影响和所需投入分配注意力，把工作分为快速收益、大项目、填充项和吃力不讨好项。
- **官方步骤 / 技巧**：逐项评估影响和投入；高影响低投入优先；高影响高投入规划后执行；低影响低投入有余力再做；低影响高投入避免或最小化。官网建议获取准确输入、定期复核，并可结合艾森豪威尔矩阵。
- **何时适用**：需求池、技术债、增长实验或运营改进的初筛。
- **AI 产品应用示例（推导）**：给 RAG 增加引用展示可能是快速收益；重建数据权限体系是高影响大项目；润色后台图标是填充项；无用户价值的全模型适配是吃力不讨好项。
- **局限 / 误用风险（推导）**：早期估算容易高估影响、低估模型评测与数据治理投入；矩阵也忽略风险和战略必要性。至少同时标证据强度、风险、依赖与置信区间。

来源：[Untools — Impact-Effort Matrix](https://untools.co/impact-effort-matrix/)

### 2.6 Ladder of inference（推论阶梯）

- **官方要义**：人会从可观察数据快速跳到选择性数据、解释、假设、结论、信念和行动；把阶梯显式化可减少武断结论。
- **官方步骤 / 技巧**：确认自己当前在哪一层；从行动向下追问依据，检查信念、结论、假设和解释；问自己忽略了什么数据与其他解释；到达底部后再有意识地向上重建推理。
- **何时适用**：访谈归因、指标异动解释、人员评价、模型失败分析，以及团队对同一事实得出冲突结论时。
- **AI 产品应用示例（推导）**：“用户没采用 → 功能没价值 → 砍掉”可能跳过了入口不可见、权限未开、结果延迟或质量不稳定等数据；先补漏斗、会话回放和访谈，再决定。
- **局限 / 误用风险（推导）**：它提升推理透明度，却不能保证底层数据完整或无偏；也可能被用来无休止质疑。评审时固定写“观察事实—解释—假设—决策—验证”。

来源：[Untools — Ladder of inference](https://untools.co/ladder-of-inference/)

### 2.7 Hard choice model（艰难选择模型）

- **官方要义**：先判断决策的影响高低与选项是否易比较，再投入相称的时间和方法。
- **官方步骤 / 技巧**：低影响且易比较是“无需纠结”，快速决定；低影响难比较看当前优先级；高影响易比较，充分收集信息；高影响难比较，接受没有唯一正确答案，比较因素并尽量做小实验降风险。
- **何时适用**：不确定一个决策是否值得深挖，或团队对小事过度分析、对大事却仓促拍板时。
- **AI 产品应用示例（推导）**：提示文案颜色是低影响易比较，限时决定；把核心工作流交给单一闭源模型属于高影响且难完全比较，应做影子流量、退出成本评估和阶段性试点。
- **局限 / 误用风险（推导）**：影响与可比性会随信息变化；把“可量化”误当“易比较”会漏掉隐私、声誉和组织能力。使用前写清时间范围和不可逆性。

来源：[Untools — Hard choice model](https://untools.co/hard-choice-model/)

### 2.8 OODA loop（观察—研判—决策—行动循环）

- **官方要义**：信息不完整、环境快速变化时，持续循环比等待完美信息更有优势。
- **官方步骤 / 技巧**：Observe 快速收集当前和上一轮反馈；Orient 结合情境、经验、多方视角分析并挑战现状；Decide 选择行动，实质上形成待验证假设；Act 实施并用结果检验前面环节；随后立即进入下一轮。
- **何时适用**：竞品动作、模型能力快速变化、线上质量波动、增长实验或事故响应。
- **AI 产品应用示例（推导）**：观察新模型在自有评测集上的增益和价格；研判迁移影响；决定给 5% 流量；行动并监测质量、成本、安全和回退；用结果开始下一轮，而不是直接全量迁移。
- **局限 / 误用风险（推导）**：追求循环速度可能牺牲安全控制；在高风险域，“行动”应是沙箱、影子或小流量实验。必须预设停止条件、回滚和责任人。

来源：[Untools — OODA loop](https://untools.co/ooda-loop/)

### 2.9 Cynefin framework（Cynefin 情境框架）

- **官方要义**：不同问题域需要不同响应，不能把所有问题都当成可分析、可预测的工程任务。
- **官方步骤 / 技巧**：清晰域用“感知—分类—响应”和最佳实践；繁杂域用“感知—分析—响应”，依赖专家；复杂域先安全试验，再感知与响应；混乱域先行动止血，再感知与响应；无序域先拆分并判断各部分所属域。
- **何时适用**：决定该标准化、专家分析、做实验还是先止血；尤其适合 AI 产品中混合了确定性软件和概率性模型的工作。
- **AI 产品应用示例（推导）**：账号鉴权是清晰域；推理成本优化是繁杂域；新型 AI 代理的人机协同是复杂域，要并行小实验；大规模越权调用是混乱域，先禁用工具权限与回滚。
- **局限 / 误用风险（推导）**：分类本身可能有争议，同一项目的子问题常落在不同域；不要给整个项目贴一个标签，应按问题拆分并在新证据出现时重分类。

来源：[Untools — Cynefin framework](https://untools.co/cynefin-framework/)

### 2.10 Confidence determines speed vs. quality（置信度决定速度—质量权衡）

- **官方要义**：产品研发对速度或质量的偏好，应取决于对“问题重要性”和“方案正确性”的置信度，并以数据而非主观看法为基础。
- **官方步骤 / 技巧**：问题重要性置信度低，偏速度以快速学习；问题与方案置信度都高，偏质量；问题置信度高但方案置信度低，在速度与质量间平衡。置信度是连续尺度，选择也应有梯度。
- **何时适用**：原型做到多真、是否建设生产级平台、该先人工运营还是完全自动化等资源权衡。
- **AI 产品应用示例（推导）**：尚未证明用户需要“自动写投研报告”时，用人工编排 + API 原型快速验证；需求已稳定且方案通过评测后，再投入权限、审计、缓存、SLA 与容灾。
- **局限 / 误用风险（推导）**：低问题置信度不等于可以低安全质量；安全、隐私和数据隔离是底线。把置信度拆为需求证据、任务成功率、技术可行性和运营可控性。

来源：[Untools — Confidence determines speed vs. quality](https://untools.co/confidence-determines-speed-vs-quality/)

## 3. 逐项精读：问题解决（8 项）

### 3.1 Ishikawa Diagram（石川图 / 鱼骨图）

- **官方要义**：用结构化分类罗列复杂问题的潜在根因，而不把最先想到的原因当成答案；一个问题可能有多个根因。
- **官方步骤 / 技巧**：定义问题并画主干；列贡献因素或类别，既可自定，也可参考人员、设备、方法、测量、材料、环境；对每类反复问“为什么”；最后分析根因候选，补证据或优先验证最可能的原因。
- **何时适用**：结果异常但成因跨人、流程、数据、模型和系统；适合工作坊或个人分析。
- **AI 产品应用示例（推导）**：线上回答正确率下降，按数据质量、检索、提示词、模型版本、工具调用、评测口径、用户分布和基础设施分支展开；为各候选根因补版本差异、追踪日志和分群数据。
- **局限 / 误用风险（推导）**：图上只是原因假设，不是因果证明；类别会诱导遗漏或重复。每条根因需附证据状态、验证方法和负责人，避免凭投票定真相。

来源：[Untools — Ishikawa Diagram](https://untools.co/ishikawa-diagram/)

### 3.2 Abstraction laddering（抽象阶梯）

- **官方要义**：初始问题陈述通常不是唯一或最佳框架；向上问“为什么”扩大范围，向下问“如何”形成更具体的问题或方案。
- **官方步骤 / 技巧**：把初始问题写在中间；连续问“为什么”得到更抽象的目标；从任一层连续问“如何”走向具体表述和解法。可在设计过程任意阶段快速使用，也可团队工作坊使用。
- **何时适用**：需求过早绑定功能、问题范围过窄或过宽、团队需要重新框定机会。
- **AI 产品应用示例（推导）**：“做一个聊天机器人”向上追问得到“让客服更快解决高重复问题”；再向下可得到知识检索、答案草稿、相似工单推荐或自动分流，不再被聊天界面限制。
- **局限 / 误用风险（推导）**：向上过多会变成空泛使命，向下过早又回到方案锁定。每一层用用户行为、业务结果和边界条件校验，并明确本轮决定在哪一层解决。

来源：[Untools — Abstraction laddering](https://untools.co/abstraction-laddering/)

### 3.3 Conflict Resolution Diagram（冲突消解图 / Evaporating Cloud）

- **官方要义**：表面互斥的主张背后通常有不同需要，但更高层可能共享同一目标；揭示假设后可设计同时满足双方需要的双赢方案。
- **官方步骤 / 技巧**：从右向左写双方互斥要求；分别问要求满足什么需要；找同时满足两种需要后实现的共同目标；讨论把原主张变成互斥的假设；从共同目标与双方需要出发重建方案。
- **何时适用**：产品与技术、业务与安全、速度与质量等争论长期僵持，接受任一原提议都会牺牲另一方需要时。
- **AI 产品应用示例（推导）**：业务要求全自动 Agent 以降本，安全团队要求完全不自动操作。共同目标是“可持续提高服务效率”；需要分别是规模收益与可控风险；新方案可限定低风险任务、最小权限、人工确认高风险动作并设审计与回滚。
- **局限 / 误用风险（推导）**：并非所有冲突都有可兼得方案，资源、法规或价值冲突可能真实存在；“共同目标”不能被写得空泛来压制异议。无法兼得时应显式升级权衡和决策权。

来源：[Untools — Conflict Resolution Diagram](https://untools.co/conflict-resolution-diagram/)

### 3.4 Zwicky box（兹威基盒 / 形态分析）

- **官方要义**：复杂创新问题不能只靠熟悉解法；把系统拆成相互独立的关键属性，再强制组合各属性取值，可系统地产生完整方案。
- **官方步骤 / 技巧**：先清楚定义问题；识别关键且逻辑独立的属性（可逆向拆解现有例子）；把属性设为列并为每列穷举取值，暂不筛选；从每列选一个值，系统、随机或聚焦地生成组合；保持开放，奇怪组合也可能启发创新。
- **何时适用**：多维产品形态、商业模式、交互方式或技术架构探索，传统脑暴开始重复时。
- **AI 产品应用示例（推导）**：用“目标角色 × 触发方式 × 输出形态 × 自动化程度 × 数据源 × 收费方式”组合 AI 分析产品，产生“财务经理 + 定时触发 + 异常解释 + 人工确认 + 企业数据仓库 + 按席位收费”等可检验概念。
- **局限 / 误用风险（推导）**：组合数会爆炸，属性不独立或缺关键维度会产生伪创新；原站也强调输出只是原始想法，仍需筛选和打磨。先设安全与可行性硬约束，再用证据筛选。

来源：[Untools — Zwicky box](https://untools.co/zwicky-box/)

### 3.5 Productive Thinking Model（生产性思考模型）

- **官方要义**：在问题已经定义、需要创意解法时，用六步结构把理解、成功标准、问题重写、发散、收敛和执行连接起来。
- **官方步骤 / 技巧**：①“发生了什么？”理解问题、影响、已有信息、相关人和目标未来；②“成功是什么？”用 DRIVE 明确方案要做到什么、不能做什么、可投资源、价值和必要结果；③“问题是什么？”形成“How might we”催化问题；④不评判地生成大量答案；⑤按成功标准选择并增强方案，可借助决策矩阵；⑥对齐行动、资源和责任人。
- **何时适用**：问题边界已有基本共识，但团队需要从问题走到可执行的创新方案。
- **AI 产品应用示例（推导）**：为“提高销售通话复盘采用率”定义目标未来和成功门槛；形成“如何让经理在 3 分钟内获得可信、可追溯的辅导建议”；发散摘要、风险片段、问题模板等；按准确率、可解释性和实施资源筛选，最后落实数据、评测和负责人。
- **局限 / 误用风险（推导）**：如果前置问题定义错误，六步只会高效解决错误问题；发散与评分还可能被同质团队偏见主导。先用抽象阶梯、访谈和数据校验问题，步骤间保留回退。

来源：[Untools — Productive Thinking Model](https://untools.co/productive-thinking-model/)

### 3.6 Inversion（反向思考）

- **官方要义**：不要只想理想解；想象最坏决定、失败路径或问题的反面，可发现应规避的条件。
- **官方步骤 / 技巧**：问“最糟的决定 / 方案是什么”；写下它为什么糟；从这些失败原因反推好方案。辅助问题包括“会如何出错”“相反是什么”“什么会构成坏方案”。项目中可做预演失败：假设六个月后失败，再追问发生了什么、犯了什么错、为什么失败。
- **何时适用**：发布前风险审查、架构设计、数据治理、安全评审、重大商业承诺。
- **AI 产品应用示例（推导）**：预演“Agent 上线三个月后造成客户损失”；失败原因可能是广泛写权限、无确认、无追踪、错误重试和指标只看完成率；据此反推最小权限、分级确认、幂等、审计和损失指标。
- **局限 / 误用风险（推导）**：易被悲观主义绑架，列出所有风险却不区分概率与影响。用风险等级、预警信号、缓解措施和风险接受人收敛。

来源：[Untools — Inversion](https://untools.co/inversion/)

### 3.7 Issue trees（问题树 / 方案树）

- **官方要义**：把大问题分成更小、可管理的部分，用“分而治之”确定优先分析处；问题树回答“为什么”，方案树回答“如何”。
- **官方步骤 / 技巧**：问题树按类别拆分，追求 MECE（相互独立、完全穷尽）；先覆盖大类而非陷入具体假设；用 80/20 聚焦最重要部分，尽量基于数据；选中分支后问“如何改善”，建立方案类别并在其中生成想法。
- **何时适用**：需求模糊、指标下降、复杂故障、商业目标或技术问题需要拆解和分工时。
- **AI 产品应用示例（推导）**：“AI 助手任务成功率低”可拆为用户目标不清、输入上下文不足、检索失败、推理失败、工具执行失败、验收口径错误；按失败贡献定位重点，再为检索失败建立查询改写、索引更新、权限可见性等方案树。
- **局限 / 误用风险（推导）**：现实原因可能交叉，机械追求 MECE 会藏掉反馈关系；树也容易把假设伪装成事实。每个叶节点标数据口径、证据和剩余覆盖率，涉及循环时转用连接圆。

来源：[Untools — Issue trees](https://untools.co/issue-trees/)

### 3.8 First principles（第一性原理）

- **官方要义**：把问题拆到不能再分解的基本事实，再从这些事实重建方案，而不是沿用类比和行业惯例。
- **官方步骤 / 技巧**：先拆成基本真相，再从其重建方案；可用“五个为什么”追根；也可用苏格拉底式提问：澄清含义、质疑假设、追问理由 / 证据、推演影响、寻找不同视角、反问原问题。
- **何时适用**：惯例成为约束、成本或架构看似不可改变、需要突破性的产品与技术设计时。
- **AI 产品应用示例（推导）**：不先假设“AI 产品必须是聊天框”，而从事实重建：用户要在原工作流内更快完成明确任务、模型输出有不确定性、结果需验证；因此方案可能是表格批量补全、代码内联建议或审批流，而非对话。
- **局限 / 误用风险（推导）**：团队常把未经验证的信念误称为基本事实；过度从零重建会忽略成熟标准和历史经验。为每个“第一性”标证据来源，优先复用已验证的安全和工程实践。

来源：[Untools — First principles](https://untools.co/first-principles/)

## 4. 逐项精读：系统思考（5 项）

### 4.1 Iceberg Model（冰山模型）

- **官方要义**：事件只是水面；向下依次看事件、长期模式、系统结构和心智模型，才能从“发生什么”走到“为什么发生”，越深通常杠杆越大。
- **官方步骤 / 技巧**：事件层问“现在发生什么”；模式层问“长期发生什么、趋势是什么”；结构层问“什么影响模式、模式如何连接”；心智模型层问“哪些价值、信念或假设塑造系统”。官网提醒，尤其是心智模型需要研究，不能直接观察。
- **何时适用**：相同缺陷、投诉、返工或经营问题反复出现，团队一直打补丁却无法阻止复发。
- **AI 产品应用示例（推导）**：事件是知识助手一次高风险幻觉；模式是知识库每次更新后幻觉上升；结构是索引直接上线、无版本化回归评测；心智模型是“延迟上线比错误回答更糟”。杠杆点是变更管理、质量闸门和速度—可信度准则，而不只是修一条答案。
- **局限 / 误用风险（推导）**：四层不是自动成立的因果链；心智模型最易变成对他人动机的猜测。用访谈、制度和决策记录验证，事故仍先止血；不是每个问题都必须归因到文化。

来源：[Untools — Iceberg Model](https://untools.co/iceberg-model/)

### 4.2 Connection circles（连接圆）

- **官方要义**：把系统关键变量和直接因果关系放在圆周上，可理解复杂性并识别强化或平衡反馈回路。
- **官方步骤 / 技巧**：画圆；选对系统变化重要、会增减、可用名词描述的关键元素，且不超过 10 个；找直接因果并画箭头，以“+ / −”标目标变量同向或反向变化；关系可基于数据或假设；寻找闭合回路。
- **何时适用**：多个指标互相影响、局部优化带来意外副作用、产品—研发—运营需要共同画出因果假设时。
- **AI 产品应用示例（推导）**：成功率 → 用户信任 → 使用量 → 反馈样本 → 模型质量 → 成功率是潜在强化环；但使用量也会增加边界工单 → 人工响应变慢 → 不满上升 → 信任下降，形成约束环。每条边标“已证实 / 待验证”。
- **局限 / 误用风险（推导）**：“+ / −”不表示效应大小、置信度或时滞；10 个元素也可能漏外生变量。图是因果假设而非证明，需要实验、日志、访谈或时序分析验证关键箭头。

来源：[Untools — Connection circles](https://untools.co/connection-circles/)

### 4.3 Concept map（概念图）

- **官方要义**：把概念或系统中的实体及其关系可视化，使心智模型显性化、暴露知识缺口，并帮助多人发现理解差异和对齐。
- **官方步骤 / 技巧**：在已有基本领域知识的前提下，先写焦点问题；列通常 15–25 个关键实体；从一般到具体排序；把实体放到可移动便签上，用线和明确连接词描述关系；持续补全，任意相连实体应能读成有意义的句子，发现知识缺口就补研究。
- **何时适用**：新领域上手、需求建模、架构沟通、权限与数据关系复杂、跨职能词义不一致。
- **AI 产品应用示例（推导）**：围绕“企业助手如何只回答用户有权访问的知识”，映射用户、用户组、身份系统、文档、ACL、连接器、切片、索引、过滤器、LLM、引用和审计；如果画不清 ACL 更新如何传播到索引，就暴露了待定义需求。
- **局限 / 误用风险（推导）**：概念图不直接表达动态反馈、概率、吞吐和时滞；多人达成一致也不等于事实正确。焦点问题过宽或连接词只写“相关”会让图失去可操作性。

来源：[Untools — Concept map](https://untools.co/concept-map/)

### 4.4 Balancing feedback loop（平衡 / 调节反馈回路）

- **官方要义**：系统检测期望水平与实际水平的差距，并触发反向纠正行动，让系统趋于稳定；识别具体回路的关键是找到它的目标，目标可能是隐性的。
- **官方步骤 / 技巧**：明确目标 / 期望水平、实际水平和二者差距；找由差距触发且让实际值回到目标附近的纠正行动；同时检查与之共存的强化回路。
- **何时适用**：质量阈值、SLA、成本预算、安全风险、人审比例、限流与容量控制，以及解释增长为何遇到平台。
- **AI 产品应用示例（推导）**：目标是成功任务成本 ≤ ¥0.20 且成功率 ≥ 85%；成本超标时压缩上下文、缓存或路由小模型，成功率跌破门槛时路由高能力模型或升级人工，形成相互约束的调节机制。
- **局限 / 误用风险（推导）**：单一或错误目标会让系统稳定在错误状态；监控和纠正时滞会造成振荡；指标可能被优化穿透。目标必须成组表达用户结果与护栏，不要过早把探索型产品强行稳定。

来源：[Untools — Balancing feedback loop](https://untools.co/balancing-feedback-loop/)

### 4.5 Reinforcing feedback loop（强化反馈回路）

- **官方要义**：回路中变量互相强化，一轮输出成为下一轮输入并放大效果，因此产生指数式上升或下降；现实系统通常同时存在强化与平衡回路。
- **官方步骤 / 技巧**：找至少两个互相强化的内部变量；检查输出是否进入下一轮并放大；区分内部变量和只改变输出的外部变量；同时寻找限制它的平衡回路。
- **何时适用**：增长飞轮、数据网络效应、模型学习闭环，以及技术债、投诉、成本或信任的恶化螺旋。
- **AI 产品应用示例（推导）**：任务成功 → 信任 → 使用 → 高质量反馈 → 评测 / 训练数据改善 → 更高成功率。反向也可能变成低质 → 低信任 → 少使用 → 少反馈 → 改进更慢，因此早期要保证最小可信体验和可学习反馈。
- **局限 / 误用风险（推导）**：增长不会无限指数持续，容量、市场、预算和合规会形成平衡回路；更多使用也不必然带来好数据，偏差和奖励投机反而会被放大。共同上涨不是因果，仍须验证。

来源：[Untools — Reinforcing feedback loop](https://untools.co/reinforcing-feedback-loop/)

## 5. 逐项精读：沟通（2 项）

### 5.1 Situation-Behavior-Impact（SBI：情境—行为—影响）

- **官方要义**：反馈若夹带对动机的判断，接收者容易防御；把具体情境、可观察行为和实际影响分开，可使反馈更清楚、非评判化。既可用于负面反馈，也可用于正面反馈。
- **官方步骤 / 技巧**：先说明行为发生的具体情境；只描述看到的行为而非解释；说明行为对自己、他人或团队的影响；必要时询问对方意图，讨论意图与影响的差距；鼓励对方反思以后如何改变。
- **何时适用**：代码 / 方案评审、跨职能协作、事故复盘、绩效辅导，以及需要对 AI 输出质量给可行动反馈时。
- **AI 产品应用示例（推导）**：“在昨天 Agent 方案评审（情境），你展示了总体成功率但未披露高风险任务样本和失败分类（行为），导致团队无法判断自动执行边界并延后审批（影响）。当时是数据还没准备好，还是你认为这部分不影响决定（意图）？”
- **局限 / 误用风险（推导）**：陈述“影响”仍可能偷渡归因；SBI 不能替代根因分析或系统改进，也不适合把所有组织问题个人化。用可观察事实和可核验影响，给对方解释空间。

来源：[Untools — Situation-Behavior-Impact](https://untools.co/situation-behavior-impact/)

### 5.2 Minto Pyramid（金字塔原理）

- **官方要义**：商业沟通要自上而下：先结论 / 建议，再给关键论点，最后用事实、数字和结果支撑；忙碌受众即使不读细节也能得到核心信息。
- **官方步骤 / 技巧**：先写最重要结论（BLUF）；用简短关键点解释“为什么”；最后按需给证据和细节。如果关键论点已足够且受众能理解，可省略部分细节。
- **何时适用**：PRD 摘要、技术决策记录、模型评测报告、风险升级、经营复盘和管理层汇报。
- **AI 产品应用示例（推导）**：结论：“暂不全量上线，先扩到 20% 低风险流量”；关键理由是高风险场景事实一致性未达门槛、单位成本仍超预算；细节再附分群评测、置信区间、失败样本和成本表。
- **局限 / 误用风险（推导）**：结论前置不等于省略不确定性；错误结论会因表达清楚而更有说服力。必须让论点能追溯到证据，给反例、限制和决策条件留位置。

来源：[Untools — Minto Pyramid](https://untools.co/minto-pyramid/)

| **研发实施** | 做多快、做到多好？团队如何按风险和价值执行？ | [置信度决定速度—质量](https://untools.co/confidence-determines-speed-vs-quality/)、[艾森豪威尔矩阵](https://untools.co/eisenhower-matrix/)、[OODA](https://untools.co/ooda-loop/)、[SBI](https://untools.co/situation-behavior-impact/)、[Minto 金字塔](https://untools.co/minto-pyramid/)、[冲突消解图](https://untools.co/conflict-resolution-diagram/) | 原型 / MVP / 生产级定义；任务排序；实验节奏；评审反馈；风险升级和决策记录。门：验收、评测、观测、权限、回滚是否与风险等级相称？ |
| **上线运营 / 复盘** | 真实世界发生了什么？怎样止损、学习、扩张或调整？ | [OODA](https://untools.co/ooda-loop/)、[Cynefin](https://untools.co/cynefin-framework/)、[石川图](https://untools.co/ishikawa-diagram/)、[冰山模型](https://untools.co/iceberg-model/)、[连接圆](https://untools.co/connection-circles/)、[强化反馈回路](https://untools.co/reinforcing-feedback-loop/)、[平衡反馈回路](https://untools.co/balancing-feedback-loop/)、[SBI](https://untools.co/situation-behavior-impact/)、[Minto 金字塔](https://untools.co/minto-pyramid/) | 在线质量 / 成本 / 风险看板；事故处置；根因与系统结构；飞轮 / 恶化环；下一轮假设。门：继续放量、保持、回滚还是终止？ |

### AI 产品的六个专有叠加层

每个阶段都要在通用思考工具之上，额外回答以下六组问题；否则“产品正确”不等于“AI 产品可用”。

1. **数据可得性与治理**：训练、评测、检索和反馈数据从哪来？是否合法、有权限、可追溯、够新鲜？数据分布与真实用户一致吗？
2. **模型能力与评测**：任务成功如何定义？基准集、分群、失败分类、人工裁决、线上指标和版本回归如何设计？
3. **随机性、幻觉与安全**：错误能否被发现和恢复？提示词注入、越权、偏见、隐私泄漏、内容安全和不可逆动作如何限制？
4. **人机协同**：AI 是建议、草稿、执行还是自治？何时确认、拒绝、转人工、申诉和覆盖？责任如何归属？
5. **延迟、成本与可靠性**：端到端延迟、吞吐、单次成功任务成本、供应商依赖、降级和容灾门槛是什么？
6. **反馈与数据飞轮**：什么反馈真能改善产品？如何避免低质量、选择偏差或奖励投机的数据被强化？

### RACI 式最小责任分配

- **问题是否值得解决**：业务管理是 A，AI 产品经理是 R，需求分析师与技术负责人是 C。
- **成功、护栏与评测定义**：AI 产品经理和技术负责人共同 R；业务管理对价值与风险接受 A；需求、工程、运营 C。
- **技术与数据方案**：技术负责人 A/R，工程师 R，产品与需求 C。
- **上线 / 放量 / 回滚**：风险低时产品与技术共同 R；高风险时业务或指定风险负责人 A，运营负责执行与监控。
- **事故复盘与系统修复**：技术负责人 A，相关工程 / 运营 R，产品与业务参与结构和激励层改进。

RACI 不能靠思维工具自动生成；它用于防止“大家都参与，但无人负责”。

## 8. 可复用的端到端工作流

### 第 1 步：识别情境和投入级别

- 用 [Cynefin](https://untools.co/cynefin-framework/) 判断清晰、繁杂、复杂、混乱或无序；复杂域先做安全试验，混乱域先止损。
- 用 [艰难选择模型](https://untools.co/hard-choice-model/) 判断影响与可比性，决定花多少研究和决策成本。
- **输出**：情境分类、可逆性、决策截止日、决策人、研究 / 试验预算。

### 第 2 步：从表面请求重构真实问题

- 用 [抽象阶梯](https://untools.co/abstraction-laddering/) 从“要一个功能”向上追问目标，再向下产生不同解法。
- 用 [推论阶梯](https://untools.co/ladder-of-inference/) 分开观察、选择的数据、解释、假设和结论。
- 用 [概念图](https://untools.co/concept-map/) 对齐角色、实体、流程、数据、权限和关系。
- **输出**：一页问题简报、焦点问题、概念图、事实 / 假设 / 未知清单。

### 第 3 步：诊断根因和系统动力

- 用 [冰山模型](https://untools.co/iceberg-model/) 从事件走到模式、结构与心智模型。
- 用 [连接圆](https://untools.co/connection-circles/) 画关键变量、直接因果和闭环。
- 用 [石川图](https://untools.co/ishikawa-diagram/) 穷举多类根因候选，再用 [问题树](https://untools.co/issue-trees/) 按数据贡献拆分和排序。
- **输出**：根因候选、证据状态、反馈回路、最高价值验证计划。

### 第 4 步：定义成功、护栏和可验证问题

- 用 [生产性思考模型](https://untools.co/productive-thinking-model/) 的“发生什么—成功是什么—问题是什么”定义 Target Future 和 DRIVE 标准。
- 明确核心用户结果、业务结果、模型质量、成本、延迟、安全、隐私和人工升级护栏。
- **输出**：成功标准、不可接受结果、评测方法、停止 / 回滚条件。

### 第 5 步：发散完整方案而非堆功能

- 用 [第一性原理](https://untools.co/first-principles/) 去除未经验证的惯例。
- 用 [兹威基盒](https://untools.co/zwicky-box/) 组合角色、触发、交互、自动化、数据、模型和商业模式。
- 用 [六顶思考帽](https://untools.co/six-thinking-hats/) 补数据、机会、风险、情绪、创意与流程视角。
- **输出**：3–5 个真正不同的方案，每个方案注明目标用户、价值、AI 角色、依赖、风险和验证方法。

### 第 6 步：收敛、投资和计划

- 先用 [反向思考](https://untools.co/inversion/) 做失败预演，设硬门槛。
- 可比方案用 [决策矩阵](https://untools.co/decision-matrix/)；再用 [二阶思考](https://untools.co/second-order-thinking/) 检查长期后果。
- 用 [影响—投入矩阵](https://untools.co/impact-effort-matrix/) 排方案和需求；用 [置信度决定速度—质量](https://untools.co/confidence-determines-speed-vs-quality/) 决定做原型、平衡型 MVP 或生产级系统。
- **输出**：决策记录、评分与敏感性分析、MVP 边界、资源和里程碑。

### 第 7 步：实施、反馈和跨职能协作

- 用 [艾森豪威尔矩阵](https://untools.co/eisenhower-matrix/) 管理立即做、排期、委派和取消。
- 用 [SBI](https://untools.co/situation-behavior-impact/) 给具体、非评判反馈；出现目标冲突时用 [冲突消解图](https://untools.co/conflict-resolution-diagram/) 找共同目标和隐藏假设。
- 用 [Minto 金字塔](https://untools.co/minto-pyramid/) 记录“结论—理由—证据”。
- **输出**：迭代计划、责任人、决策日志、风险升级、评审结论。

### 第 8 步：灰度上线、运营和复盘

- 用 [OODA](https://untools.co/ooda-loop/) 连续观察、研判、决策、行动；高风险动作只在沙箱、影子流量或小流量中学习。
- 用 [平衡反馈回路](https://untools.co/balancing-feedback-loop/) 维持质量、成本、延迟和风险目标；用 [强化反馈回路](https://untools.co/reinforcing-feedback-loop/) 观察增长飞轮与恶化螺旋。
- 事故先按 Cynefin 止损，之后用石川图和冰山模型复盘；将结果回填到第 1–4 步。
- **输出**：放量 / 保持 / 回滚 / 停止决定，线上学习，系统修复与下一轮假设。

## 9. 五套高复用组合打法

### 9.1 反复出现的问题：诊断链

`概念图 → 冰山模型 → 连接圆 → 石川图 → 问题树`

1. 概念图先统一实体和边界；2. 冰山从单一事件寻找长期模式和结构；3. 连接圆显式化反馈关系；4. 石川图扩展根因候选；5. 问题树用数据定位贡献最大的分支。  
适用：模型质量反复波动、客服工单增长、交付总延期。来源：[Concept map](https://untools.co/concept-map/)、[Iceberg Model](https://untools.co/iceberg-model/)、[Connection circles](https://untools.co/connection-circles/)、[Ishikawa Diagram](https://untools.co/ishikawa-diagram/)、[Issue trees](https://untools.co/issue-trees/)。

### 9.2 从模糊需求到创新方案：重构链

`抽象阶梯 → 第一性原理 → 兹威基盒 → 生产性思考模型 → 影响—投入`

先把“功能请求”改写成用户目标，再去掉惯例约束；用多属性组合生成真正不同的完整概念；按成功标准锻造方案；最后做组合排序。  
适用：“我们也要做一个 AI 助手”这类方案先行需求。来源：[Abstraction laddering](https://untools.co/abstraction-laddering/)、[First principles](https://untools.co/first-principles/)、[Zwicky box](https://untools.co/zwicky-box/)、[Productive Thinking Model](https://untools.co/productive-thinking-model/)、[Impact-Effort Matrix](https://untools.co/impact-effort-matrix/)。

### 9.3 高影响决策：治理链

`Cynefin → 艰难选择 → 六顶思考帽 → 推论阶梯 → 决策矩阵 → 二阶思考 → 速度—质量`

先确认问题域和决策投入，展开多视角并检查证据跳跃；可比较时量化比较，不可比较时做小实验；再检查长期后果，最后决定交付强度。  
适用：模型供应商、自动化边界、是否自研、是否进入高监管行业。来源：[Cynefin](https://untools.co/cynefin-framework/)、[Hard choice](https://untools.co/hard-choice-model/)、[Six Thinking Hats](https://untools.co/six-thinking-hats/)、[Ladder of inference](https://untools.co/ladder-of-inference/)、[Decision matrix](https://untools.co/decision-matrix/)、[Second-order thinking](https://untools.co/second-order-thinking/)、[Confidence determines speed vs. quality](https://untools.co/confidence-determines-speed-vs-quality/)。

### 9.4 风险、灰度和持续学习：适应链

`反向思考 → OODA → 平衡回路 + 强化回路`

发布前先假设失败并设护栏；用小步 OODA 验证；上线后既用平衡回路守住质量、成本和安全，又观察飞轮或恶化环是否被放大。  
适用：Agent 自主执行、模型迁移、定价实验、大客户灰度。来源：[Inversion](https://untools.co/inversion/)、[OODA](https://untools.co/ooda-loop/)、[Balancing feedback loop](https://untools.co/balancing-feedback-loop/)、[Reinforcing feedback loop](https://untools.co/reinforcing-feedback-loop/)。

### 9.5 冲突到可执行共识：协作链

`冲突消解图 → SBI → Minto 金字塔 → 艾森豪威尔矩阵`

先找表面冲突背后的双方需要和共同目标；再针对具体行为与影响交换反馈；用结论—理由—证据记录共识；最后把行动分成做、排期、委派、不做。  
适用：业务要速度、技术要治理，或产品与研发争议长期不收敛。来源：[Conflict Resolution Diagram](https://untools.co/conflict-resolution-diagram/)、[Situation-Behavior-Impact](https://untools.co/situation-behavior-impact/)、[Minto Pyramid](https://untools.co/minto-pyramid/)、[Eisenhower Matrix](https://untools.co/eisenhower-matrix/)。

## 10. 会议与评审检查表

### 10.1 通用会前准备

- [ ] 本次需要做的**决定**是什么？谁是最终决策人，最晚何时决定？（艰难选择模型）
- [ ] 这是清晰、繁杂、复杂、混乱还是尚未拆开的无序问题？（Cynefin）
- [ ] 哪些是观察事实，哪些是解释、假设和结论？（推论阶梯）
- [ ] 备选项是否至少有两个？如果只有一个，是因为硬约束还是过早收敛？
- [ ] 成功结果、不可接受结果、硬门槛和待验证信号分别是什么？（生产性思考模型、反向思考）
- [ ] 材料开头是否写了“结论 / 建议—关键理由—证据”？（Minto）

### 10.2 需求评审

- [ ] 请求背后的用户、情境、任务、频率和当前替代方案是什么？
- [ ] 向上问“为什么”后，真正目标是否仍需要 AI？向下问“如何”是否出现非聊天、非 AI 或人机混合解？（抽象阶梯）
- [ ] 用户痛点是一次事件还是长期模式？背后的流程、激励或信念是什么？（冰山模型）
- [ ] 领域实体、权限、规则和异常能否在概念图上说清？
- [ ] 问题重要性的证据是什么：行为数据、访谈、付费 / 承诺、人工成本还是风险？
- [ ] “AI 能做”是否被误写成“用户需要”？是否有反证？（推论阶梯）
- [ ] 验收是否包括模型失败、拒答、转人工、权限不足和数据缺失？

### 10.3 产品方案评审

- [ ] 成功标准是否同时包含用户结果、业务结果、模型质量和护栏？
- [ ] 问题树是否基本覆盖且减少重叠？最值得解决的分支有数据支持吗？
- [ ] 是否产生了真正不同的方案，而非同一界面的微调？（第一性原理、兹威基盒）
- [ ] 六顶帽子的收益、创意、感受、数据、风险和过程视角是否都出现？
- [ ] 关键变量的因果与副作用是否被画出？哪些箭头只是待验证假设？（连接圆）
- [ ] 方案的影响、投入、证据强度、依赖和风险是否一起排序？
- [ ] AI 的自动化等级与人工介入点是否清楚？

### 10.4 技术 / 架构评审

- [ ] 数据来源、所有权、权限、保留、删除、更新和血缘是否明确？
- [ ] 模型候选是否用同一真实任务集评测，并按用户 / 语言 / 风险分群？
- [ ] 决策矩阵是否先设安全、隐私、合规等硬门槛，再比较可补偿因素？
- [ ] 是否记录总体分数背后的失败样本、置信区间和评分证据？
- [ ] 对提示词注入、越权、幻觉、供应商故障、数据漂移、重复执行做过失败预演吗？（反向思考）
- [ ] 10 分钟、10 个月和更长期的锁定、维护、成本与组织影响是什么？（二阶思考）
- [ ] 质量、延迟、成本和安全的目标—实际—差距—纠正机制是什么？（平衡回路）
- [ ] 是否有观测、版本、灰度、降级、回滚、审计和事故责任人？

### 10.5 商业 / 投资评审

- [ ] 谁获得什么可测价值，谁付费，谁承担使用和变更成本？
- [ ] 单次**成功任务**的收入、推理、数据、人工复核、支持和风险成本是多少？
- [ ] 价值和单位经济的关键假设分别如何验证？
- [ ] 是低影响 / 高影响、易比较 / 难比较中的哪类决策？投入是否相称？（艰难选择）
- [ ] 当前收益的二阶后果：侵蚀毛利、改变用户行为、供应商锁定、合规与品牌风险是什么？
- [ ] 增长飞轮的每条因果边有何证据？什么平衡回路会限制增长？
- [ ] 产品、技术、安全与业务的表面冲突背后，各自需要和共同目标是什么？（冲突消解图）
- [ ] 明确写下投资、试验、保持、退出或停止决定及其触发条件了吗？

### 10.6 上线 / 放量评审

- [ ] 问题重要性和方案正确性的置信度分别是多少，证据是什么？交付质量与之相称吗？
- [ ] 离线评测是否通过分群门槛；线上指标、护栏、告警和样本审查是否就绪？
- [ ] 是否定义灰度人群、流量阶梯、观察窗口和统计 / 人工判断方式？
- [ ] 高风险动作是否采用最小权限、确认、幂等、审计和人工升级？
- [ ] 是否准备供应商故障、超预算、质量下降、数据泄漏和错误执行的回滚 / 降级？
- [ ] 谁能暂停系统？什么阈值自动暂停？用户如何纠错、申诉和恢复？
- [ ] 放量决定是否按 Minto 记录结论、理由、证据和残余风险接受人？
- [ ] 上线后第一轮 OODA 的时间、负责人和数据源是否已安排？

### 10.7 复盘评审

- [ ] 先写可观察事实和时间线，再写解释；是否避免推论阶梯跳跃？
- [ ] 这是单次事件还是历史模式？结构和心智模型层有哪些证据？（冰山模型）
- [ ] 石川图中的根因候选各有什么支持 / 反对证据？
- [ ] 哪些反馈回路放大了问题，哪些纠正机制没有起效或因时滞失效？
- [ ] 反馈针对情境、行为与影响，还是在评价个人动机？（SBI）
- [ ] 立即修复、系统修复、研究任务和停止事项是否分开？
- [ ] 谁负责、何时验证修复有效、如何回填评测集和发布门禁？
- [ ] 复盘结论是否进入下一轮 OODA，而不是停留在文档？

## 13. 使用边界：七条防误用原则

1. **框架不是证据**：它只帮助组织问题；数据、用户研究、实验、日志和专业审查才支撑结论。
2. **事实、假设、选择必须分栏**：连接圆的一条边、鱼骨图的一条根因、冰山的一种心智模型都可能只是待验证假设。
3. **硬门槛先于加权平均**：隐私、安全、合法性和不可逆风险不能被高商业分数抵消。
4. **数字不等于客观**：决策矩阵和影响—投入矩阵要附评分证据、置信度与敏感性分析。
5. **AI 的平均表现不够**：必须看分群、长尾、失败严重度、人工升级和版本变化。
6. **一个系统不只有一个回路**：强化增长总会遇到限制，调节机制也可能造成振荡或稳定在错误目标。
7. **工具服务决策，不替代问责**：每次评审都要有决策人、风险接受人、停止条件、责任人和复查日期。

## 14. 来源与覆盖审计

- **官方总索引**：[Untools 首页](https://untools.co/)；研究时同时用其官方 Gatsby 数据端点 [`/page-data/index/page-data.json`](https://untools.co/page-data/index/page-data.json) 核对名称、分类、正文和 slug。
- **分类核对**：[决策制定 10 项](https://untools.co/decision-making/)、[问题解决 8 项](https://untools.co/problem-solving/)、[系统思考 5 项](https://untools.co/systems-thinking/)、[沟通 2 项](https://untools.co/communication/)。
- **逐项核验**：本文第 2–5 节的每一项都附对应 Untools 官方页面，合计 **25 个不同工具页面**。
- **覆盖结果**：25/25，100%；截至研究日期无未覆盖项。Untools 网站未来可能新增、删改或重分类工具，复用本文时可用官方索引重新计数。

---

这套方法的核心不是“每次把 25 个工具全用一遍”，而是持续完成四个动作：**把观察与假设分开、按问题类型选择响应、让方案和风险都可验证、把上线反馈带回下一轮决策**。对 AI 产品而言，最重要的加法是：任何用户价值判断都同时经过数据权限、模型评测、随机性与安全、人机边界、成本延迟和反馈质量六层检查。
